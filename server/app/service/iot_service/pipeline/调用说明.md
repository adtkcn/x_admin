# iot/pipeline 调用说明

设备报文**处理层**（iot.md 第一层：数据处理流水线）。接入层（HTTP/MQTT/TCP/WS）只组装标准信封 `iot_schema.IngestMsg` 并投递队列，本包异步消费并落地。

## 一、总体链路

```
接入层 → core.Queue("iot:ingest") → pipeline.HandleIngest(worker)
        → 刷新运行态/在线转换
        → 可视化规则链逐节点执行：触发 → 解码 → 过滤 → 并行/布尔路由 → 告警/状态快照/历史存储/通知…（大屏数值不经节点，由定时器统一冲刷脏集合推送）
```

在线方向由报文实时驱动（首条报文即上线），离线方向由到期表（ZSET）驱动，快/慢两条路径由定时任务触发。
包内依赖单向：`online ← alert ← rulechain ← pipeline`，`store` 为叶子旁路（时序落库、唯一数据出口）。

## 二、对外门面（调用方均在 pipeline 包外）

| 导出函数 | 调用方 | 时机 |
| --- | --- | --- |
| `HandleIngest(ctx, body)` | `app/queue/iot.go`（并发 3 消费 `iot:ingest`） | 每条报文一次 |
| `ScanOffline()` | `app/corn` → `iotOfflineScan`（每 5 秒） | 快路径：原子弹出到期表已过窗成员并置离线 |
| `SweepOffline()` | `app/corn` → `iotOfflineSweep`（每 5 分钟） | 慢路径：全扫库侧在线设备，超窗置离线、缺失/过期 score 回填，重建到期表 |
| `CleanData()` | `app/corn` → `iotDataClean`（每天 03:00） | 按 `IOT.DataKeepDays` 分批清理时序历史（0=永久保留） |
| `PushScreenTick()` | `app/corn` → `iotScreenPush`（每 2 秒） | 冲刷大屏脏集合 `push:dirty`，按区域房间批量推 `iot:telemetry`（无观众早退） |
| `Runtime(deviceId, timeout)` | `iot_controller/device.go`（`/device/state`） | 管理端读 Redis 运行态快照 |
| `QueryRange(deviceId, startMs, endMs, limit)` | `device.go` | 管理端时序区间回读（趋势图/链路验证），ts 倒序 |
| `StopRuntime(deviceId)` | `device.go` | 删设备后清其 Redis 运行态，避免幽灵设备 |
| `StopAlertRuntime(deviceId)` | 删告警历史的控制器 | 只清设备告警运行态：活动态存的是历史记录主键，删库不删键会让后续命中永不新建告警 |
| `StopSink()` | `main.go`（优雅关闭，队列停后、DB 关前） | 冲刷存储缓冲剩余数据落库 |

> 开关：`queue_schema.QueueIotIngest = "iot:ingest"`；`IOT.Enable=false` 时不注册消费者，`HandleIngest`/`ScanOffline`/`SweepOffline` 空转。
> 离线收尾/删设备的告警清理**不是导出函数**，而是 `alert` 子包 `init` 经 `online.OnDeviceOffline`/`OnDeviceClear` 钩子注册（详见五、六）。

## 三、报文消费主流程（pipeline.go）

1. `HandleIngest` 反序列化 `IngestMsg`；坏报文或缺 `device_id` 返回错误由队列记日志（不重试，避免死循环）。
2. `online.RefreshOnline`：所有报文类型都 `keepAlive` 续命；发生「离线→在线」时 `MarkStatus(1)` 写库并广播 `iot:status`，**写库失败则撤销刚写入的到期 score**（靠下一条报文重新触发上线，不补扫）。
3. 按 `MsgType` 分派：`telemetry` → `handleTelemetry`；`heartbeat` 仅续命。
4. `handleTelemetry` 从产品缓存 `CachedProductModel` 取规则链 ID 与物模型属性白名单，转调 `rulechain.Run`。

> **产品/规则链两级读缓存**（本包与 `iot_service` 共同提供，热路径零 Redis 往返）：
> `CachedProductModel` 与 `CachedParsedTree` 都遵循「本进程内存（TTL=`LocalCacheTTL`，默认 60s）→ Redis（TTL=`ThingCacheTTL`，默认 600s）→ DB」两级回源，命中即返回；规则链本内存层直接缓存已解析的 `*iot_schema.RuleTreeNode`，一并抹平 JSON 重解析。
>
> **跨实例即时失效（pubsub）**：管理端 `InvalidateProductCache` / `InvalidateChainCache` 除了删 Redis，还通过 `core.IotBus`（频道前缀 `{RedisPrefix}iot:bus:`）广播 `product`/`chain` 事件；各实例 `iot_service.init` 中的订阅回调收到后 `core.CacheDelete / CacheDeletePrefix` 清本内存。`LocalCacheTTL` 仅作广播未达时的兜底。

## 四、规则链执行（`rulechain/`：rulechain.go + rc_nodes.go + decode.go）

引擎已抽为子包，直接 import 同为子包的 `online`/`alert`/`store`（三者都不反向依赖本包，故无需早期 `SetDeps` 注入）。父包 `handleTelemetry` 只转调 `rulechain.Run`。

图与执行树：产品 `rule_chain_id` → `iot_service.RuleChainService.CachedParsedTree`（本内存→ Redis 原文 → DB 两级回源，本内存层 TTL=`LocalCacheTTL`），命中直接给 `*iot_schema.RuleTreeNode` 指针，每条报文只走内存指针、不做 JSON 解析与库查询。
- 拓扑：链即树，触发器为唯一根，除并行节点外每节点至多一条出边（保存时 `checkGraph` 约束）。执行树由前端从 LogicFlow 图展开后直接以 `tree_data` 提交，后端 `CachedParsedTree` 中 `json.Unmarshal` 为 `iot_schema.RuleTreeNode`，不再做图→树展开。
- 遍历：`walk` 直接下钻 `children`，运行期不再查节点/出边表；`halt`（整条报文短路标记）放在以指针嵌入、复制上下文时共享的 `rcShared` 里，任一分支 halt 即停所有兄弟分支。链不存在/停用/无触发器 → 按未配置丢弃。
- 分支隔离：并行分叉（多 children）时每条分支拿深拷贝负载，解码/改写互不干扰；单线不复制。
- 注册表 `rcHandlers`：handler 只回答「本分支是否继续下钻」，新增节点 = 注册 handler + schema 加属性 + 前端加面板；未知类型按「继续下钻」兜底。

| 节点 | 行为 | 下钻 |
| --- | --- | --- |
| `trigger` | 配 `msg_types` 时只放行命中类型 | 放行下钻，否则 halt |
| `decode` | goja `run(values, sn)` 覆盖 values，空则丢弃 | 下钻 / halt |
| `filter` | goja `run(values, sn)`，false 丢弃整条 | 下钻 / halt |
| `bool` | goja 判定，false 只剪本分支（不 halt） | 下钻 / 剪枝 |
| `parallel` | 分流由树结构表达，自身无副作用 | 全部下钻（唯一显式多分支） |
| `alarm` | goja `run(values)` 返回级别，交 `alert.EvalAlert` 收敛（告警记录/广播的 values 按物模型白名单裁剪） | 全部下钻 |
| `state` | `online.SaveLatestValues` 写 Redis 最新属性快照（按白名单裁剪）；并标脏 `push:dirty`供定时推大屏 | 全部下钻 |
| `history` | `store.Write` 批写时序表（落库前按物模型白名单裁剪） | 全部下钻 |
| `notify` | 站内/邮件/webhook（后两者走异步队列） | 全部下钻 |

goja 脚本契约（decode.go）：各脚本节点统一实现全局函数 `run(values, sn)`（后端固定调用 run），空脚本=透传。解码 `run`→属性对象；过滤/布尔 `run`→布尔；告警 `run`→级别数字（只认数字，其它按不告警；0=不告警/恢复；-1=故障、1=轻微、2=严重，3+ 预留；故障危害最轻但优先接管）。按 `产品:类型:节点ID:阶段` **缓存编译产物，每条报文新建 Runtime**（goja 非并发安全），异常统一 recover，单条失败不拖垮 worker。

## 五、告警状态机（`alert/`）

报文驱动的事件级收敛（异常=有数据，无需另起到期扫描）。`rulechain` 告警节点直调 `alert.EvalAlert`；本包 `init` 把离线收尾/删设备清态注册为 online 钩子。

- **两条独立事件流**：故障(-1)与普通阈值告警(1/2/…)各维护一条「告警中」记录，互不合并、严格分离。每条报文只确认其一，另一条流即收恢复信号：`level==-1` 确认故障流并对普通流发恢复、`level>0` 确认普通流并对故障流发恢复、`level==0` 两条流都发恢复；被切的流按恢复确认时长收尾，确认期切回则计时作废。普通记录 `severity` 取事件内命中过的最高档（只升不降）。当前级别未变的重复命中不落库。
- 支持 `duration`（首次只记起点，跨过后触发）与 `recover`（恢复正常需连续满该时长才收尾，期间再命中计时作废）。
- 落库经 `AlertService.Raise/Recover/UpdateSeverity`。WS `iot:alarm` 推**设备聚合级**（`deviceAlarm`：故障优先 -1，否则普通流当前级别；与 `MapList` 口径一致），仅当聚合级变化才推——延迟恢复期两条流并存，按单流推会误清或降级。
- Redis 键（前缀见六）：普通流 `alert:active|first|recover:<id>`、故障流 `alert:fault:active|first|recover:<id>`（active 为 "<主键>:记录峰值级别:当前级别"，无 TTL；first/recover 为对应计时起点）。两流六键一次 MGet 读出。

## 六、运行态与在线判定（`online/`：runtime.go + offline*.go + hooks.go）

只认运行态本身、不反向依赖告警。`hooks.go` 定义 `OnDeviceOffline`/`OnDeviceClear` 两个钩子注册点，由 `alert` 子包 `init` 注册回调（`closeOnOffline`/`ClearRuntime`），从而打破 online ↔ alert 循环依赖。父包 `pipeline.go` 保留 `ScanOffline`/`SweepOffline`/`Runtime`/`StopRuntime` 门面，对外零改动。

运行态全放 Redis，键前缀 `{RedisPrefix}iot:`（统一走 `RuntimeKey`）：
- `expire:zset` 到期表：**在线判定唯一事实源**，`keepAlive` 每条报文 `ZADD score=now+窗口`；缺失/到期=离线→在线。
- `state:<id>`（最新属性快照，`SaveLatestValues` 写）、`seen:<id>`（最后报文接收时间，TTL 长于窗口，供慢路径重建到期表）。
- 窗口 `offlineWindow` 取设备 `offline_timeout`（无宽限期），未配置落 `DefaultOfflineTimeout`。
- 广播：`BroadcastStatus`/`BroadcastAlarm` 逐事件实时推；大屏数值由 `PushScreenTick` 定时冲刷 `push:dirty` 脏集合批量推 → 房间 `iot:device:<id>`（单设备）、`iot:map:<spaceId>`（区域大屏）。
- Redis 异常时 `keepAlive` 保守返回 false，避免依赖故障时每条报文 SELECT+UPDATE 拖垮 DB。

## 七、时序存储出口（`store/`：按增删查分文件）

规则链「历史存储」节点唯一出口，**换库只改本包**。包内按职责拆分：`store.go`（架构说明）、`write.go`（增：`Write`/批写缓冲/`Flush`）、`query.go`（查：`QueryRange`）、`clean.go`（删：`Clean`）。对外 `Write` 供 rulechain 直调，`Flush`/`QueryRange`/`Clean` 经父包门面 `StopSink`/`QueryRange`/`CleanData` 供 main/controller/corn 调用。

本期以 MySQL 顶替 iot.md 第四阶段的 TDengine：
- **values 受物模型约束**：约束统一由 `iot_schema.ScopeValues(values, allow)` 实现（`allow`=物模型 identifier 白名单，来自 `CachedProductModel.ThingIds`），供**时序存储 `store.Write`、运行态快照 `online.SaveLatestValues`、告警记录 `alert.EvalAlert` 三处共用**；`allow` 空（未配或解析不出）则不约束原样落地；时序存储裁空则跳过本行并记 WARN。约束位于各存储层而非规则链节点，本包不查库、不引 service 依赖。
- 表只存 `values`（加工后已约束的属性），**不写 `origin` 列**；初始上报值只作 decode 入参在内存流转，不落库。
- `Write` 先投内存缓冲（chan 容量 2048），后台协程按「攒满 `DataBatchSize` 或 2 秒」批量落库；缓冲满退回同步单写不丢数，批写失败只记日志（极小概率丢批可接受）；首条数据才惰性 `startBatcher`，流水线未启用不留空转任务。

## 八、配置（config/iot.go）

`Enable` / `IngestConcurrency`（消费并发，代码固定 1）/ `DeviceCacheTTL` / `ThingCacheTTL`（图与物模型 Redis 层 TTL）/ `LocalCacheTTL`（本内存层 TTL，产品模型与解析好的执行树共享，pubsub 广播未达时的兜底）/ `StateTTL` / `MaxValues` / `PushStateChange`（WS 广播开关）/ `LogRaw`（联调打开）/ `DataBatchSize` / `DataKeepDays`。

## 九、扩展速查
