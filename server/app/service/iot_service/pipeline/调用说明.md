# iot/pipeline 调用说明

设备报文**处理层**（iot.md 第一层：数据处理流水线）。接入层（HTTP/MQTT/TCP/WS）只负责组装标准信封 `iot_schema.IngestMsg` 并投递队列，本包异步消费并落地。

## 一、总体链路

```
接入层 → core.Queue("iot:ingest") → pipeline.HandleIngest(worker)
        → [刷新运行态/在线转换]
        → [可视化规则链逐节点执行：触发 → 解码 → 过滤 → 并行/布尔路由 → 告警/状态快照/历史存储/大屏推送/通知…]
```

在线方向由报文实时驱动（首条报文即上线），离线方向由到期表（ZSET）驱动，快/慢两条路径由定时任务触发。

## 二、入口与调用点（谁调用本包）

本包对外只暴露这些函数，调用方全部在 `pipeline` 包外：

| 导出函数 | 调用方 | 触发时机 |
| --- | --- | --- |
| `HandleIngest(ctx, body)` | `app/queue/iot.go` 的 `IotStart` | 消费 `iot:ingest` 队列，每条报文一次（`queue/start.go` 以并发度 3 注册 `core.Queue.Consume`） |
| `ScanOffline()` | `app/corn/fixed_task.go` → `iotOfflineScan` | 快路径，每 5 秒：原子弹出到期表已过窗成员并置离线 |
| `SweepOffline()` | `app/corn/fixed_task.go` → `iotOfflineSweep` | 慢路径，每 5 分钟：全扫库侧在线设备，超窗置离线、缺失/过期 score 回填，重建到期表 |
| `CleanData()` | `app/corn/fixed_task.go` → `iotDataClean` | 每天 03:00：按 `IOT.DataKeepDays` 分批清理时序历史（0=永久保留） |
| `Runtime(deviceId, timeout)` | `admin_ctl/iot_controller/device.go` | 管理端「状态快照」回读（`/device/state`），读 Redis 运行态 |
| `QueryRange(deviceId, startMs, endMs, limit)` | `admin_ctl/iot_controller/device.go` | 管理端时序历史区间回读（趋势图/链路验证），ts 倒序 |
| `StopRuntime(deviceId)` | `admin_ctl/iot_controller/device.go` | 设备删除后清理其 Redis 运行态，避免幽灵设备 |
| `StopSink()` | `main.go`（优雅关闭序列，队列停后、DB 关前） | 把存储缓冲里剩余数据同步落库 |
| `CloseAlertsOnOffline` | `hooks.go` 经 `online.OnDeviceOffline` 钩子注册，离线转换时回调 | 设备离线时收尾活动告警 |

> 队列名与开关：`queue_schema.QueueIotIngest = "iot:ingest"`；`IOT.Enable=false` 时 `start.go` 不注册消费者、`IotStart`/`ScanOffline`/`SweepOffline` 直接空转。

## 三、报文消费主流程（pipeline.go）

1. `HandleIngest` 反序列化 `IngestMsg`；坏报文返回错误由队列记日志（不重试，避免死循环）。
2. `device_id` 为空直接丢弃。
3. `online.RefreshOnline`：所有报文类型（心跳/上报）都会 `keepAlive` 续命；发生「离线→在线」转换时 `MarkStatus(1)` 写库并广播 `iot:status`。**写库失败撤销刚写入的到期 score**（`cancelDeadline`），靠下一条报文重新触发上线，不自愈补扫。
4. 按 `MsgType` 分派：`telemetry` → `handleTelemetry`；`heartbeat` 仅续命不再处理。
5. `handleTelemetry` 从产品缓存读出规则链 ID 与物模型属性白名单（`CachedProductModel`），交给 `rulechain.Run`（子包）。

## 四、规则链执行（`rulechain/` 子包：rulechain.go + rc_nodes.go + decode.go）

规则链执行引擎已抽为 `pipeline/rulechain` 子包，**直接 import** 同为子包的 `online`（状态快照/大屏推送）、`alert`（告警收敛）、`store`（时序落库）：三个子包都不反向依赖本包，构成 online ← alert ← rulechain ← pipeline 的单向 DAG，已无需早期的 `SetDeps` 注入式解耦。父包 `pipeline.go` 对外的 `handleTelemetry` 只转调 `rulechain.Run`。

- 图来源：产品 `rule_chain_id` → `RuleChainService.CachedGraphRaw`（Redis 缓存原文）→ 子包再缓存一层「解析好的规则链树」（原文变或超 `ThingCacheTTL` 才重解析），保证每条报文只走内存指针。
- 拓扑：链在语义上就是树——触发器为唯一根，除并行节点外每节点至多一条出边（保存时由 `checkGraph` 约束）。解析阶段 `parseTree` 把 LogicFlow 邻接图展开成 `rcStep` 根树，邻接表仅作临时中间量；展开时 `onPath` 防环、`rcMaxDepth` 防超深、`rcMaxSteps` 防报文放大，畸形链在解析阶段即判无效（同一节点被多条路径引用即扇入，展开成多份副本，与“每条路径各跑一次”语义一致）。
- 遍历：`walk` 直接下钻 `children`，运行期不再查节点表/出边表；`halt` 为整条报文的短路标记，放在以指针嵌入 `ruleCtx` 的 `rcShared` 里（字段提升使 handler 仍写 `ctx.halt`，但复制上下文时共享同一实例），所以任一分支 `halt` 后所有兄弟分支立即停止。链不存在/停用/无触发器 → 按「未配置」丢弃。
- 分支隔离：并行分叉（`len(children) > 1`）时每条分支拿到深拷贝后的属性负载，分支间的解码/改写互不干扰；单线（≤ 1 后继）无兄弟分支，直接沿用当前上下文不复制。
- 节点处理器注册表 `rcHandlers`，handler 只回答「本分支是否继续下钻」（不再感知链拓扑）；新增节点类型 = 注册 handler + schema 加属性 + 前端加面板，不改主遍历；未知类型按「继续下钻」兜底。

| 节点 | 行为 | 下钻策略 |
| --- | --- | --- |
| `trigger` 触发器 | 配 `msg_types` 时只放行命中类型 | 放行则下钻，否则 `halt` |
| `decode` 解码 | goja `decode(values, sn)` 覆盖 values，空则丢弃 | 下钻 / `halt`（空产出） |
| `filter` 数据过滤 | goja `filter(values, sn)`，false 丢弃整条 | 下钻（true）/ `halt`（false） |
| `bool` 条件路由 | goja 判定，false 只剪本分支（不 halt） | 下钻 / 剪枝 |
| `parallel` 并行 | 分流完全由树结构（多 children）表达，自身无副作用 | 全部下钻（唯一显式多分支） |
| `alarm` 告警 | goja `alert(values)` 返回级别，交 `alert.EvalAlert` 收敛 | 全部下钻 |
| `state` 状态快照 | `online.SaveLatestValues` 写 Redis 最新属性 | 全部下钻 |
| `history` 历史存储 | `store.Write` 批写时序表（落库前按物模型白名单裁剪） | 全部下钻 |
| `push` 大屏推送 | `online.BroadcastTelemetry` 广播到区域地图房间 | 全部下钻 |
| `notify` 通知 | 站内/邮件/webhook（邮件、webhook 走异步队列） | 全部下钻 |

### goja 脚本契约（rulechain/decode.go）

脚本约定定义同名全局函数，空脚本=透传/默认值，不阻断链路：
- `decode(raw, sn)` → 属性对象；`filter(values, sn)` → 布尔；`alert(values, sn)` → 级别数字（只认数字，返回其它类型一律按不告警；0=不告警/恢复；数值即危害升序 -1=故障、1=轻微、2=严重，3+ 预留；故障危害最轻但优先于其他告警）。
- **编译一次（`Program` 按 `产品:类型:节点ID:阶段` 缓存），每条报文新建 Runtime**（goja 非并发安全）；异常/栈溢出统一 `recover`，单条失败不拖垮 worker。

## 五、告警状态机（`alert/` 子包）

报文驱动的「事件级」收敛（异常=有数据，无需另起到期扫描）：已抽为 `pipeline/alert` 子包，`rulechain` 告警节点直调 `alert.EvalAlert`；本包 `init` 自行把离线收尾/删设备清态注册为 online 钩子（closeOnOffline/ClearRuntime），不再经父包 hooks.go 中转。
- 级别 0=恢复；已在事件中则看该不该改写同条 `severity` 并重推：新级别覆盖优先序更高（危害升级，或故障接管一切）、或当前是故障而本次不再是（故障退场后把记录交还实际命中级别）；其余重复命中不落库/广播。
- 支持 `duration`（持续时长，首次只记起点，跨过后才触发）与 `recover`（恢复确认时长，恢复正常需连续满该时长才收尾，期间再命中则计时作废）。
- 落库经 `AlertService.Raise/Recover/UpdateSeverity`，转换点推 `iot:alarm`（带 `alert_id`/`severity`，前端合并「触发→升级→恢复」）。
- **单事件可改写语义**：一台设备同时只维护一条「告警中」记录；级别比的是覆盖优先序（`iot_model.AlertPriority`）而非裸数值，故障危害最低但能接管任何在告事件。
- Redis 键：`alert:active:<id>`（"<主键>:级别"，无 TTL）、`alert:first:<id>`（持续计时起点）、`alert:recover:<id>`（恢复计时起点）。设备离线由本包 `closeOnOffline`（经 online 钩子）收尾。

## 六、运行态与在线判定（`online/` 子包）

在线/离线运行态已抽为 `pipeline/online` 子包（`runtime.go`/`offline.go`/`hooks.go`），只认运行态本身、不反向依赖告警；离线转换与删设备的告警收尾由父包 `hooks.go` 的 `init` 经 `OnDeviceOffline`/`OnDeviceClear` 钩子回调，打破 online ↔ alert 循环依赖。父包 `pipeline.go` 保留 `ScanOffline`/`SweepOffline`/`Runtime`/`StopRuntime` 门面，对外调用零改动。

运行态全放 Redis，键前缀 `{RedisPrefix}iot:`（键名统一走 `RuntimeKey`）：
- `expire:zset`（到期表，**在线判定唯一事实源**）：`keepAlive` 每条报文 `ZADD score=now+窗口`；`ZSCORE` 缺失/到期=离线→在线。
- `state:<id>`（HASH 最新属性快照，由 `SaveLatestValues` 写）、`seen:<id>`（最后报文接收时间，TTL 必长于窗口，供慢路径重建到期表）。
- 窗口 `offlineWindow` 直接取设备 `offline_timeout`（无宽限期），未配置落 `DefaultOfflineTimeout`。
- 广播：`BroadcastStatus`/`BroadcastTelemetry`/`BroadcastAlarm` 落房间 `iot:device:<id>`（单设备）、`iot:map:<spaceId>`（区域大屏）。
- 读回 `ReadDeviceState`（父包门面 `Runtime` 转调）；删设备 `ClearDeviceRuntime` 清态后经 `OnDeviceClear` 钩子收尾告警。
- Redis 异常时 `keepAlive` 保守返回 false，避免依赖故障时每条报文都 SELECT+UPDATE 拖垮 DB。

## 七、时序存储出口（`store/` 子包）

规则链「历史存储」节点唯一出口（`store.Write`，由 rulechain 直调）；`Flush`/`QueryRange`/`Clean` 经父包门面 `StopSink`/`QueryRange`/`CleanData` 供 main/controller/corn 调用。本期以 MySQL 顶替 iot.md 第四阶段的 TDengine：
- **`values` 受物模型约束**：`Write` 落库前按调用方传入的 `allow`（产品物模型 identifier 白名单，来自 `CachedProductModel`）裁剪，只保留已建模属性；`allow` 为空（未配物模型或旧形态解析不出）则不约束、原样落地；裁剪后为空则跳过本行并记 WARN。本包不查库、不引入 service 依赖。
- 表中只存 `values`（加工后且已约束的属性），**不再写 `origin` 列**；初始上报值只作为 decode 的入参在内存流转，不落库。
- `store.Write` 先投内存缓冲（chan 容量 2048），后台协程按「攒满 `DataBatchSize` 或 2 秒」批量落库；缓冲满退回同步单写，不丢数；批写失败只记日志（极小概率丢批可接受）。
- 惰性启动（首条数据才 `startBatcher`），流水线未启用不留空转任务。
- **换库只改 `store` 子包**（`batchCreateRows`/`QueryRange`/`Clean`），其余不受影响。

## 八、相关配置（config/iot.go）

`Enable` / `IngestConcurrency`（消费并发，代码固定 3）/ `DeviceCacheTTL` / `ThingCacheTTL`（图与物模型缓存重解析周期）/ `StateTTL` / `MaxValues` / `PushStateChange`（WS 广播开关）/ `LogRaw`（联调打开）/ `DataBatchSize` / `DataKeepDays`。
